### 페이징을 배우기 이전에

이전에 메모리 할당([여기](https://bluepaper14.github.io/posts/memory/))에 대해서 배워 연속과 불연속을 기준으로 나누어 메모리를 할당할 수 있음에 배웠다. 그중 불연속 할당에 두가지가 존재하는데 <u>페이징</u>과 <u>세그먼테이션</u>이 있었다.

핵심은 메모리를 할당할때 홀 발생, 즉 단편화의 존재가 중요했다. 우리는 이를 쪼개어 내부 단편화, 외부 단편화로 나누어 메모리 낭비 종류에 대해 배웠다. 그 중 페이징은 외부 단편화는 발생하지 않고 내부 단편화는 발생하지만 매우 작으므로 유용한 기법으로 소개했다. 이제 페이징에 대해 구체적으로 알아보자.

### 논리주소와 물리주소

페이징의 크기를 확인하기 이전에 주소를 명확히 구분할 필요가 있다. 결론적으로 2종류의 주소는 이렇게 요약할 수 있는데,,

**논리주소 = "책의 페이지 번호"**

**물리주소 = "실제 종이책의 물리적 위치"**

---

### 논리주소

> 논리주소 : 프로세스가 실행 중일 때 사용하는 주소

논리주소는 메모리 공간을 참조하기 위한 주소로 CPU가 생성하여 사용자에게 보여준다. 

ex) 5쪽 3번째 줄에 문장을 쓰라는 의미

---

### 물리주소

> 물리주소 : 실제로 메모리의 특정 위치를 가리키는 주소

논리주소는 MMU에 의해 물리주소로 변환되어 실제 메모리를 접근한다.

ex) 책의 글 5쪽 3번째 줄을 보고 실제 종이 2쪽에 해당되는 것을 인쇄한다는 의미

아래 요약된 개념들이다.

| 항목           | 개념적 정의                                 | 책 비유                               |
|----------------|----------------------------------------------|----------------------------------------|
| 논리주소       | 프로그램이 참조하는 추상적인 주소            | 작가가 말하는 "5쪽 3번째 줄"           |
| 물리주소       | 실제 메모리(RAM)의 주소                      | 인쇄소에서 종이 몇 번 몇 번째 줄인지   |
| 페이지         | 논리 메모리를 나눈 단위                      | 책의 한 쪽                             |
| 프레임         | 물리 메모리를 나눈 단위                      | 종이 한 장                             |
| 페이지 테이블  | 페이지와 프레임 간의 매핑 정보                | 쪽 번호와 종이 번호 대응표             |
| MMU            | 논리주소를 물리주소로 변환해주는 하드웨어     | 작가의 말을 인쇄소에게 전달하는 비서   |

### 페이지 크기

Q.페이징에서 내부 단편화 발생 이유?

페이징 기법에서는 외부 단편화는 발생하지 않지만 내부 단편화는 생길 수 있다. 메모리는 <u>프레임 단위로만 할당</u>되기 때문에 마지막 페이지에 남는 자투리 공간은 사용할 수 없어 낭비된다. 평균적으로 프로세스당 절반 페이지 정도가 내부 단편화로 이어진다.

Q.그럼 페이지의 크기를 줄여버리면?

내부 단편화를 줄이기 위해 페이지 크기를 줄일 수 있다. 하지만 메모리 전체 크기를 줄이는 것이 아니라, 페이지 하나의 크기(즉, 쪼개는 단위)를 더 작게 만드는 것이다. 남는 공간이 작아져 단편화는 줄어들지만, 페이지 수가 많아져 관리해야 할 항목도 늘어난다.

요약하자면..

페이지 수가 많아지면 페이지 테이블이 커진다. 그만큼 테이블을 저장하는 데 필요한 메모리도 증가한다. 반면 디스크 입장에서는 페이지 크기가 클수록 I/O 효율이 좋다. 반대로 페이지 크기를 너무 작게 만드는 것도 비효율적일 수 있다다. 결국 페이지 크기는 단편화, 테이블 크기, 디스크 성능 사이의 균형을 고려해야 한다.

### 페이징 사례

프로세스는 4GB 주소 공간을 가지고 Page 크기를 4KB로 가정하자.

-> 즉 4GB의 주소 공간은 약 백만개의 page

예를 들어 사용자 프로세스(1개)는 현재 6개의 Page를 사용중이라고 하자.

-> 프로세스 크기는 24KG

- 코드(0~2)
- 데이터(2~3)
- 힙(3~4)
- 스택(마지막 page)

주소 공간의 모든 page를 6개로 항목으로 나타내자. 

```
char* p = (char*)malloc(200);
```
프로세스가 메모리를 동적할당 받을때 논리주소에서 물리주소로 변환되는 과정을 살펴보자. 현재 malloc(200)으로 200byte 메모리를 동적할당하였는데..실제 페모리 할당 단위는 페이지 단위이기 때문에 일반적으로 200byte할당도 1페이지(4KB)를 할당한다.

그럼 동적 메모리를 할당하는 힙 영역의 page 5에 할당했다고 가정하자.

1페이지당 4KB이므로 5 x 4 = 20KB 환산하면 20 x 1024 = 20480

결과적으로 malloc()은 page 5의 논리주소 20480을 반환한다.

```
*p = 'a'
```
위 식은 논리주소 20480번지에 'a'를 저장하는 코드다. page 5가 frame 2에 할당된다고 가정할때,

frame 2의 물리주소는 2 x 4KB = 8KB 환산하면 8 X 1024 = 8192

결과적으로 MMU에 의해 논리주소 20480은 물리주소 8192로 매핑된다.

### 페이징의 구현

- 하드웨어 지원

CPU는 PTBR((Page Table Base Register)를 제공한다.

- MMU 장치

page table을 참조하여 논리주소를 물리주소로 변환한다. 이 기능은 메모리보호도 역할수행.

(page 번호가 page table에 있는지 범위안에 존재하는지)

- OS는 page table 관리기능 제공

물리 메모리에 할당된 page table과 빈 frame 리스트 생성 관리 유지

### 페이지 테이블 문제점

페이지 테이블을 사용하는 메모리 관리 방식은 물리 메모리와 매핑하기 위한 필수적인 구조이지만 역시 문제가 발생한다.

<u>1.두 번의 메모리 접근 발생</u>

CPU가 논리주소를 물리 주소로 변환할때, 페이지 테이블을 참조하니, 두번의 접근이 필요하다.

(프로엠 번호 조회 + 물리 메모리 접근) -> 속도 저하

<u>1.페이지 테이블 크기</u>

실제 사용하는 메모리보다 훨씬 큰 크기의 테이블이 메모리에 존재한다. 즉 전체 주소 공간을 다 사용하지 않기에 페이지 테이블 내 많은 공간이 비어있다. -> 메모리 낭비

가장 핵심은 "2번의 메모리 접근", "큰 페이지 테이블 크기"인데 이를 해결하기 위한 방법 3가지가 있다.

---

### TLB

메모리 접근을 해결하고자 TLB를 제시했다.

>TLB : 페이지 테이블을 매번 접근하지 않고 최근 접근한 주소 변환 정보를 저장하고 빠르게 조회할 수 있도록 도와주는 장치.

- MMU 내에 존재

- 최근에 접속한 항목을 저장

- 연관 메모리 구조(병렬 검색가능. 빠른 검색가능)

- 참조의 지역성 가짐(순차적 반복적 접근패턴 유리)

TLB의 과정은 이러하다.

```
A.CPU가 가상 주소의 페이지 번호로 메모리 접근

B.TLB에서 해당 페이지 번호검색

IF Hit = 해당 페이지 번호가 있으니, 프레임 번호를 즉시 반환

IF MISS = 없으니, 페이지 테이블을 메모리에서 접근해서 프레임 번호 가져옴
```
해당 TLB 과정에서 성능을 더욱더 향상시킬 수 있는 방법이 있다. 그것은

<u>1.TLB 항목수 증가</u>

더 많은 주소 패밍 정보를 저장해서 Hit를 증가시킨다. -> 다만 하드웨어 구현 비용생각

<u>2.페이지 크기 증가</u>

한 페이지 안에서 더 많은 데이터를 접근하게 시킨다. -> 다만, 페이지 크기가 커지면 내부 단편화가 증가되어 메모리 낭비로 이어짐

### IPT

그리고 페이지 테이블 크기이다. 실제로 활용되는 페이지 테이블 비율은 매우 낮다. 이에 해결법은 2가지가 있다.

>역 페이지 테이블(IPT) : 기존의 프로세스마다 존재한 페이지 테이블을 없앤다. 시스템 전체에 하나의 페이지 테이블만 두는 방식. 물리 메모리의 프레임 기준으로하여 해당 프레임에 어떤 프로세스의 어떤 페이지가 적재되는지 결정

- 테이블 인덱스는 프레임 번호기준으로 지정
- 각 항목은 [Pid(프레임에 데이터의 프로세스ID), page number(논리 페이지 번호)] 형태로 구성
- 페이지 테이블 항목수 = 물리 프레임 수
- 테이블 전체를 순회하여 매핑을 확인 -> 검색속도 느리다.
- 페이지 테이블 크기 줄이기 가능 -> 다만 메모리 접근 여러 번 필요

### 멀티 레벨 페이지 테이블

또한 테이블 크기를 줄이기 위한 다른 방법이다.

>멀티 레벨 페이지 테이블 : 페이지 테이블 자체를 여러 단계로 나누어 계층적으로 구성. 실제 사용중인 테이블만 메모리에 유지시킨다.

- 논리 주소의 pgae 번호 부분을 여러 단계로 분할
- 페이지 디렉토리는 각 하위 페이지 테이블에 대한 포인터를 가짐
- 사용중인 하위 테이블만 메모리 유지
- 주소 공간에서의 페이지 테이블 메모리 낭비 줄임 -> 메모리 접근이 여러 단계로 늘어나면 속도저하
