### 데이베이스 설계

정규화 그리고 함수적 종속을 배우는 이유가 무엇일까 먼저 생각해보자. 먼저 아래 데이터를 보자

```
학생(StudentID), 이름(Name), 과목(Subject), 교수(Professor)

1001, 이지은, DB, 김교수  
1001, 이지은, OS, 이교수  
1001, 이지은, DB, 김교수
```
데이터는 일관성 있게 유지되어야한다. 그런데 같은 학생이 여러행으로 중복되거나 삭제 또는 수정에서 다른 원인으로 번질 수 있다. 즉 데이터들이 서로 어떤 관계로 묶여있는지 파악해야하는데..

---

###  함수적 종속

어떤 집합의 X가 속성 집합 Y를 함수적으로 결정짓는다고 할때 <u>**X의 값이 같으면 Y의 값도 반드시 같다는 의미**이다.</u>

간단한 예를 들어보자.

| 학번(StudentID) | 이름(Name) | 전공(Major) |
| ------------- | -------- | --------- |
| 202101        | 홍길동      | 컴퓨터공학     |
| 202102        | 김영희      | 전자공학      |

위 같은 테이블이 있을때, '학번은 곧 이름을 결정한다.' 또한 '학번이 곧 학생의 전공을 결정한다' 이러한 관계를 의미한다.

### 정규화

정규화를 짧게 요약하면 테이블을 작게 쪼게어 하나의 테이블이 한가지 주제만을 다루게 만드는 과정이다. 왜냐하면 중복으로 인하여 이런 문제를 해결하기 위해선 <u>스키마를 분해할</u> 필요가 있다. 

---

### 정규형

정규화에도 여러 단계가 잇다. 1차 정규형(1NF) 부터  5차 정규형(5NF)까지 있다. 차수가 높아질 수록 더 많은 제약들이 가해진다. 일반적으론 3차 정규형까지 사용한다.

### 1차 정규형

1차 정규형은 모든 속성은 원자값을 가져야 한다. 하나의 셀에는 단일한 값만 들어간다는 것.
간단한 예를 들어보면

| 학번   | 이름  | 전화번호                         |
| ---- | --- | ---------------------------- |
| 1001 | 김철수 | 010-1234-5678, 010-8888-9999 |
| 1002 | 이영희 | 010-5555-1111                |

위 테이블에서 김철수의 전화번호가 2개 이상의 값을 가지고 있다. 즉 원자값이 아니므로 1차 정규형에 위배된다.

위 1차 정규형을 만족하기 위해선 테이블을 쪼갤 필요가 있는데 아래처럼 가능하다.

- 학생테이블

| 학번   | 이름  |
| ---- | --- |
| 1001 | 김철수 |
| 1002 | 이영희 |

- 전화번호 테이블

| 학번   | 전화번호  |
| ---- | ------------- |
| 1001 | 010-1234-5678 |
| 1001 | 010-8888-9999 |
| 1002 | 010-5555-1111 |

### 2차 정규형

2차 정규형은 기존 1NF를 만족하면서 <u>**기본키의 부분집합에 종속되는 속성이 없는 정규형이다**</u>
한가지 예를 들어보자.

| StudentID | CourseID | StudentName | CourseName | Grade |
| --------- | -------- | ----------- | ---------- | ----- |
| 1001      | CS101    | 김철수         | 자료구조       | A     |
| 1001      | CS102    | 김철수         | 운영체제       | B     |
| 1002      | CS101    | 이영희         | 자료구조       | B+    |

위 테이블을 보면, 기본키인 studentID와 CourseID가 있는데 결론적으로 

StudentID가 StudentName을 결정짓지 못하고 CourseID가 CourseName을 결정짓지 못한다. 이것이 문제가 되는 이유는 만약 학생의 이름을 수정하면 모든 행을 수정해야하는 상황이 생기고 과목 이름을 추가하려면 StudentID를 임의로 지정해줘야하며 학생 한명의 모든 과목을 지우면 이름까지 날라간다.

그렇다면, 위 사항을 해결하기 위해 테이블을 쪼갤 필요가 있는데.. 아래처럼 말이다.

- 학생

| StudentID | StudentName |
| --------- | ----------- |
| 1001      | 김철수         |
| 1002      | 이영희         |

- 과목

| CourseID | CourseName |
| -------- | ---------- |
| CS101    | 자료구조       |
| CS102    | 운영체제       |


- 수강

| StudentID | CourseID | Grade |
| --------- | -------- | ----- |
| 1001      | CS101    | A     |
| 1001      | CS102    | B     |
| 1002      | CS101    | B+    |

### 3차 정규형

3차 정규형은 기존 2NF를 만족하고 <u> 키에 속사지 않은 모든 필드가 기본키에 이행 종속 되지 않아야한다</u>

말이 조금 어려운데 이행적 종속을 제거하는게 3NF이다.

> 이행적 종속 : A → B, B → C이면 A → C가 되는 경우 (C는 A에 간접적으로 종속됨)

위와 같은 이행적 종속의 문제를 확인해보자. 아래를 표를 보자.

| StudentID | Name | DeptID | DeptName |
| --------- | ---- | ------ | -------- |
| 2021001   | 이지은  | D01    | 컴퓨터공학    |
| 2021002   | 김철수  | D02    | 전자공학     |

위 테이블을 보면 studentID를 보고, Name, DeptID를 가리키고 있으며

DeptID는 DeptName을 가리키고 있다. 이렇게 되면 학과 이름을 바꾸려면 모든 학생 레코드 갱신을 해야하고 새 학과를 추가하기엔 학생이 없으면 삽입이 불가능하다. 또한 학과 소속 학생이 모두 삭제되면 학과 정보도 사라진다. 이를 해결하기 위해 정규화를 거치게 되면

- 학생 

| StudentID | Name | DeptID |
| --------- | ---- | ------ |
| 2021001   | 이지은  | D01    |
| 2021002   | 김철수  | D02    |

- 학과

| DeptID | DeptName |
| ------ | -------- |
| D01    | 컴퓨터공학    |
| D02    | 전자공학     |

이렇게 테이블을 분리함으로서 StudentID는 오직 Name과 DeptID를 결정하고
DeptID는 DeptName만 결정하게 된다.
